ELI5What are we building, in one breath?

A shop owner has a spreadsheet with hundreds of orders and doesn't want to type them in one by one. They upload the file, we check every line, and the good lines become real orders all at once.

Every line has to land exactly once. We can't create an order twice, drop one silently, or half-import a file. Most of the work in this plan is that bookkeeping.

The contract · import guide (#180)

One import, four steps

The guide is the source of truth. Where it disagrees with ADR-0010 or the PRD, the guide wins and ADR-0012 records the difference.

ELI5Why is step 3 the scary one?

Steps 1 and 2 are like reading a shopping list and crossing out lines you can't read. Nothing has happened yet. Step 3 is going to the till: once an order exists, a warehouse may start packing it.

So we wait for two things: every staged row is written, and stock is reserved for all of them. Either can finish first, and we must end up in the same place either way.

Where this lives: PR 05 (max effort).

ELI5Why this order?

It's like building a house. 01 teaches our code to read the file. 03 gives each import a place to wait. 02 writes the rules for a good row. 04 is the moment the merchant says "yes, import it". Only after that can 05 write orders, 06 reserve stock, and 07 clean up when something goes wrong.

08 is the ribbon-cutting. It only happens once everything else stands.

D8 · mega PR experiment

How it ships

The first slices are normal PRs. Everything after them lands as one PR with one commit per ticket, stacked on #205. If that gets unbearable, it splits back into separate PRs.

ELI5Why one giant PR?

Six small boxes stacked on each other means every time the bottom box changes, you re-pack all the boxes above it. One big box with six labelled envelopes inside avoids that. Reviewers can still open one envelope (one commit) at a time.

The cost: the box is heavy to review in one go. That's why it's labelled an experiment, with a way back.

ELI5What does PR 04's "confirm" mean?

The staged rows are a draft. Confirming is the merchant saying "yes, these are the orders." From that moment the draft is locked: rows can't change, and the import has one outcome.

If they press the button twice, nothing is imported twice. If our server crashes halfway, it picks up where it left off instead of leaving a half-done import.

Trap from the 02 review: nothing owns expiry for abandoned drafts today. 04 must assign it.

One model throughout

How each slice gets built

One workflow per wave. Agents edit and verify; only the orchestrator and Rui touch git.

Every report contains

  • Worktree, branch, base SHA, and whether origin/main moved
  • Files changed, with reasoning for each open judgement call
  • Tests run, passed, and not run (with why)
  • Contradictions with the handoff or the guide
  • A one-line conventional commit message and the diff stat

Mega branch now

  • Worktree .worktrees/order-import-mega on #205 (e5f6a7b8)
  • Integration DB for the whole branch: order_import_mega_test
  • 03 verified: unit and integration suites green, lint clean
  • 04: agent running → adversarial review → fix → verify → commit
ELI5Why a hostile reviewer, and why no git for agents?

One helper builds the thing. A second helper's only job is to try to break it, the way a tester pokes at a bridge before cars drive over. A third fixes whatever broke. Nobody gets to lock the result in; that's Rui's (or the orchestrator's) call after reading the report.

Keeping git out of the helpers' hands means a confused helper can make a mess in its sandbox, but it can't ship that mess.

Non-negotiables

Guardrails

Every agent

  • No commit, push, PR, stash pop or branch mutation
  • Locate code by symbol; handoff line numbers are advisory
  • No defensive guards on internal contracts, no comments by default, no skipped tests
  • Only the commit service writes orders; nothing else touches the orders table
  • No production data: imports run against fixtures only
  • Targeted tests while iterating; one integration run at the end

Publication (04, 05, B1)

  • They change public API behaviour or schemas
  • Regenerate the OpenAPI snapshot and inspect the diff
  • No new public endpoint beyond the import resource
  • Progress fields stay UI-only (D6)

Hands off

  • No git worktree remove/prune, branch -d/-D, stash drop/pop/clear, gc
  • Nothing moved under .worktrees/ or .claude/handoffs/ except own order-import worktrees

Inputs

  • Sample files: test/fixtures/imports/ (synthetic, no real merchant data)
  • Existing single-order validator: validateOrder
ELI5What does "publication" mean here?

Some changes show up in the public menu other developers read (the API docs and SDKs). Adding a dish to that menu is a promise. So whenever a slice touches the API, we regenerate the menu and read it, to make sure only what we meant to promise is on it.

Being behind a login is not the same as being off the menu. That's a separate check.
